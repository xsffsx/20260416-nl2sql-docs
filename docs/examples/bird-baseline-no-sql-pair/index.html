BIRD Baseline: From an Empty POC to Rhesis Evaluation

Created: 2026-10-24 · Updated: 2026-10-25

Rhesis baseline: 7/30 exact BIRD matches (23.3%). All 30 questions completed; there were 0 SQL execution errors and 0 metric errors. Mean BIRD Soft F1 was 0.2802. No human reviews are recorded.

NO SQL PAIR KNOWLEDGE

SQL Pair Knowledge: NOT USED. The Snapshot, actual retrieval, and generation inputs all verify this.

  • Question only: BIRD evidence was not sent to NL2SQL.
  • Gold SQL: scoring only. The Rhesis Code Metric receives it; the API request does not.
  • Fixed evaluation data: a fresh POC project with 5 tables and 30 questions.

We started with an empty proof-of-concept (POC) project, uploaded the BIRD debit-card data, published a queryable configuration, then used the Rhesis UI to send 30 question-only requests to the existing NL2SQL REST API. Rhesis applied the pinned BIRD Code Metric to compare each generated result with its Gold SQL.

This is the question-only Rhesis baseline. The separate BIRD Without SQL Pair: 30-Record Analysis Opik reports 9/30 from an evidence-assisted run; its inputs and outputs differ, so do not combine that score with this one. The 23.3% result describes these 30 debit-card questions, not all business questions or the full BIRD leaderboard.

For all 30 questions, the Rhesis verdicts, Gold and actual results, API proof, and SQL comparisons, open BIRD Without SQL Pair: 30-Record Analysis Rhesis.

For the separate run with BIRD evidence as the judge's expected_response, see BIRD Without SQL Pair: 30-Record Evidence Rhesis. Its semantic categories are separate from official BIRD Execution Accuracy.

This page walks through the POC setup, Rhesis run, official score, and external comparison. Screenshots and downloadable Rhesis records make the run reviewable without opening the local Rhesis service.

1. Start with an isolated empty project​

The project is bird_baseline_20261024. An administrator prepared a separate query database, an upload role, and a separate read-only scoring role. Business tables were then created through the product's upload interface.

The previous debit-card project already contained tables with the same names. We preserved that project and used a new empty project to prevent existing data or knowledge from influencing the run. Initially, it had no Active Snapshot and no registered or unregistered tables with the target names.

A Snapshot is the fixed business configuration used by this run. Every question was checked against the same version to avoid mixing configurations within one experiment.

2. Prepare table data and questions as separate inputs​

Table data came from the official BIRD SQLite archive and was exported to five CSV files. Questions and reference SQL came from a pinned revision of the official PostgreSQL question set. Sources, checksums, and approved column-name mappings were recorded. All 30 reference queries were independently executed successfully against the imported database.

Uploading table data makes the database queryable. Registering the evaluation dataset defines which questions to ask and how to score the answers.

  • Question is the natural-language request.
  • Evidence is the official business explanation or calculation hint. It is preserved for review but was not sent in this question-only run.
  • Gold SQL is the official reference query. Only the independent scorer receives it; it does not enter the model request.
  • SQL Pair Knowledge contains retrievable historical question/SQL examples. This run did not use it.

“Question only” means BIRD evidence was withheld. The active NL2SQL configuration and its SQL Pair exclusion are documented in the run evidence.

3. Import → Review CSV → Create schema​

Confirm the project in Artifact → Schema. Open Guide at the bottom left and choose Schema & QA → Import schema. Click Import, select CSV data · POC, and select the five CSV files. This option imports queryable data rows; CSV model metadata only imports model definitions.

Click Review CSV and check each table's name, types, samples, and row count. We explicitly selected TEXT for yearmonth.date: values such as 201208 represent year-month strings, and the source stores them as text. Type choices affect query meaning and results; automatic inference needs review.

The confirmation screen should show 5 tables · 423050 rows. Click Create schema to import the data and create a Draft. The configuration is not yet published for new questions.

4. Deploy → Publish: move the draft to Active​

After import, Schema contains five tables, but the header still shows No Active Snapshot. Click Deploy to open the Snapshot workspace and review the draft. Deploy alone does not publish it.

Click Publish, review the content, then publish in the final confirmation dialog. We named the Snapshot BIRD debit baseline · no SQL Pair so it can be identified later. Wait until Current Snapshot shows Active.

5. Check readiness before running questions​

Open Check readiness from the Guide, then click Refresh report in Diagnostics. Active identifies the selected configuration; ready / QA available means the system can currently run it. A readiness check neither submits a question nor establishes answer correctness.

Before evaluation, we confirmed the imported data, successful Gold self-checks for all 30 questions, and the published Snapshot.

VERIFIED ABSENCE OF SQL PAIR KNOWLEDGE
  1. Snapshot: no SQL Pair entries.
  2. Actual retrieval: no SQL Pair selected.
  3. Actual generation input: empty SQL knowledge.

Stages that did not execute were marked separately; missing records cannot stand in for proof of empty knowledge.

6. Create the Test Set and run it in Rhesis​

The Rhesis Test Set holds all 30 questions. prompt_content is the only API input; expected_response stores Gold SQL for scoring. BIRD evidence is not part of the Test Set CSV used in this run. The separate evidence CSV is for human review only.

Download the Rhesis Test Set CSV

The Test Set is bound to the existing NL2SQL API — BIRD question only REST Endpoint and the deterministic BIRD Official Execution Accuracy Code Metric. Each request is POST /api/nl2sql?projectId=bird_baseline_20261024 with {"query": "<question>"}; Rhesis reads the generated SQL from $.sql. Gold SQL and evidence are not included in the request.

  1. Choose the existing NL2SQL endpoint and Fresh Outputs to call the API for each case.
  2. Choose Parallel and Test Set Metrics. The run archive records the configured concurrency, but the maximum simultaneous API calls was not measured.
  3. Preflight: No skips the optional UI checks; readiness and Gold self-checks were verified separately.
  4. Run the Test Set. Rhesis recorded 30 new API outputs and applied the BIRD Code Metric; it did not use an LLM judge.

7. Why executable SQL can still fail​

Rhesis stores the SQL returned by the API and the metric result for each question. The official BIRD Code Metric executes Gold and generated SQL against the same fixed PostgreSQL data, then compares the complete results. A query can run successfully and still return the wrong columns or values.

All 30 requests and metric evaluations completed, with 0 SQL execution errors. The 23 failures are result mismatches, not SQL execution failures. Soft F1 helps inspect partial value overlap; it does not change the official Pass or Fail verdict.

9. Compare with external results​

The Mini-Dev → PostgreSQL section of the BIRD website and author reports were checked on 2026-10-24. The following are published reference scores; this run is not inserted into their ranking.

SystemPostgreSQL EXScope and key conditions
SDIP + gemini-3.8-flash69.00%500 questions, native PostgreSQL; authors report adding rules after reviewing development/test failures, so this is not an entirely unseen-question evaluation
FrontierSQL + gpt-oss-120b56.80%500 questions, one candidate, at most two repairs; test-baseline failures were reviewed during development
Ontology2SQL65.80%500 questions; SQLite predictions deterministically adapted and replayed on PostgreSQL, rather than regenerated as PostgreSQL SQL
Current Rhesis baseline23.30%30 debit-card questions, CSV POC; question-only, no SQL Pair, no BIRD evidence

These reports use execution-result scoring, but question coverage, inputs, models, data ingestion and types, knowledge configuration, generation budgets, and development exposure differ. This Rhesis run sent only the question; BIRD evidence was omitted. CSV ingestion also does not recreate every primary/foreign key or index in the native database.

EXTERNAL SCORES ARE REFERENCE POINTS, NOT A DIRECT RANKING

This Rhesis run covers 30 debit-card questions in a CSV POC; the external reports cover 500 Mini-Dev questions. This run sent no BIRD evidence; models, data, knowledge, and generation/repair budgets also differ. The effect of adding SQL Pair Knowledge has not been measured in a controlled comparison.

Percentage-point differences do not measure performance under identical conditions or isolate the effect of evidence, the model, or SQL Pair Knowledge. The case results point to output columns, filtering and aggregation, and numeric precision as areas to investigate; this run does not establish how much any change would improve results.

A fair comparison can proceed in two stages. First, align published predictions to the same 30 questions, data, and scorer, comparing only EX from frozen outputs. To assess complete Mini-Dev performance, separately run the official 500 questions and native databases. Prediction replay cannot compare generation latency or replace the unperformed with/without-SQL-Pair experiment.

Prepare and start a new evaluation from the repository

Run the Test Set from the Rhesis UI: import the question-only CSV, map prompt_content to the request question and expected_response to the scoring reference, bind the existing NL2SQL REST Endpoint and BIRD Official Execution Accuracy Code Metric, then choose Fresh Outputs, Parallel, and Test Set Metrics. Keep the endpoint request limited to the question. Configure the scoring connector with read-only database access in the target environment; credentials are not included here.

The complete local run archive is in docs/20261024_evaluation/rhesis/. Public readers can reproduce the Test Set and inspect the executed connector, official scorer sources, CSV exports, and checksums from the links above.
