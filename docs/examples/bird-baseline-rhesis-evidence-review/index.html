BIRD evidence
NL2SQL actual SQL
ratio of customers who pay in EUR against customers who pay in CZK = count(Currency = 'EUR') / count(Currency = 'CZK').
SELECT
  COUNT(*) FILTER(WHERE
    c.currency = 'EUR') AS eur_customers,
  COUNT(*) FILTER(WHERE
    c.currency = 'CZK') AS czk_customers,
  ROUND(
    CAST(COUNT(*) FILTER(WHERE
      c.currency = 'EUR') AS DECIMAL) / NULLIF(COUNT(*) FILTER(WHERE
      c.currency = 'CZK'), 0),
    4
  ) AS eur_to_czk_ratio
FROM customers AS c
WHERE
  c.currency IN ('EUR', 'CZK')

Rhesis judge explanation

The SQL directly answers the question by computing the ratio of EUR-paying customers to CZK-paying customers: ROUND(COUNT(*) FILTER (WHERE c.currency = 'EUR')::NUMERIC / NULLIF(COUNT(*) FILTER (WHERE c.currency = 'CZK'), 0), 4) AS eur_to_czk_ratio. This matches the expected evidence formula count(Currency = 'EUR') / count(Currency = 'CZK'), with the numerator being EUR and denominator CZK as requested ('EUR against CZK'). The WHERE c.currency IN ('EUR','CZK') clause correctly restricts the population, the NUMERIC cast ensures decimal division, and NULLIF only guards against division by zero without altering the calculation. The extra columns eur_customers and czk_customers are supporting detail and do not make the answer wrong per the evaluation rules.

{
  "query": "What is the difference in the annual average consumption of the customers with the least amount of consumption paid in CZK for 2013 between SME and LAM, LAM and KAM, and KAM and SME?"
}

Run proof: Rhesis status Fail · API success · execution ok

Test result ID: 4a0293fb-f18f-4482-9196-74bf126c6b80 · API trace ID: 5150bc669e7f41e852b98e6fdb6e2d07

BIRD evidence
NL2SQL actual SQL
annual average consumption of customer with the lowest consumption in each segment = total consumption per year / the number of customer with lowest consumption in each segment; Difference in annual average = SME's annual average - LAM's annual average; Difference in annual average = LAM's annual average - KAM's annual average; Year 2013 can be presented as Between 201301 And 201312; The first 4 strings of the Date values in the yearmonth table can represent year.
WITH annual_avg AS (
  SELECT
    ym.customer_id,
    c.segment,
    AVG(ym.consumption) AS annual_avg_consumption
  FROM yearmonth AS ym
  INNER JOIN customers AS c
    ON c.customer_id = ym.customer_id
  WHERE
    c.currency = 'CZK' AND ym.date LIKE '2013%'
  GROUP BY
    ym.customer_id,
    c.segment
), least_per_segment AS (
  SELECT
    segment,
    customer_id,
    annual_avg_consumption,
    ROW_NUMBER() OVER (PARTITION BY segment ORDER BY annual_avg_consumption ASC, customer_id ASC) AS rank_no
  FROM annual_avg
), segment_values AS (
  SELECT
    MAX(annual_avg_consumption) FILTER(WHERE
      segment = 'SME') AS sme_least_avg,
    MAX(annual_avg_consumption) FILTER(WHERE
      segment = 'LAM') AS lam_least_avg,
    MAX(annual_avg_consumption) FILTER(WHERE
      segment = 'KAM') AS kam_least_avg
  FROM least_per_segment
  WHERE
    rank_no = 1
)
SELECT
  sme_least_avg,
  lam_least_avg,
  kam_least_avg,
  sme_least_avg - lam_least_avg AS sme_minus_lam,
  lam_least_avg - kam_least_avg AS lam_minus_kam,
  kam_least_avg - sme_least_avg AS kam_minus_sme
FROM segment_values

Rhesis judge explanation

The SQL correctly applies the population and time filters (c.currency = 'CZK', ym.date LIKE '2013%', consistent with the evidence's year-prefix hint) and outputs the three requested differences in the evidence's directions (SME-LAM, LAM-KAM, KAM-SME). However, its core calculation contradicts the expert evidence: the CTE 'annual_avg' computes AVG(ym.consumption) per customer (an average of monthly rows, i.e., average monthly consumption) and 'least_per_segment' picks exactly one customer via ROW_NUMBER, whereas the evidence defines the metric as 'total consumption per year / the number of customer with lowest consumption in each segment' — i.e., annual totals averaged across all customers tied for lowest consumption in each segment. This changes both the scale of the metric (monthly average vs. annual total) and the tie handling (single arbitrary pick vs. averaging all tied lowest customers), so the resulting differences do not implement the requested calculation.

WITH segment_consumption AS (
  SELECT
    c.segment,
    SUM(CASE WHEN LEFT(ym.date, 4) = '2012' THEN ym.consumption ELSE 0 END) AS consumption_2012,
    SUM(CASE WHEN LEFT(ym.date, 4) = '2013' THEN ym.consumption ELSE 0 END) AS consumption_2013

    ON c.customer_id = ym.customer_id
  WHERE

  GROUP BY
    c.segment
)
SELECT
  segment,
  consumption_2012,
  consumption_2013,
  ROUND(
    (
      consumption_2013 - consumption_2012
    ) / NULLIF(ABS(consumption_2012), 0) * 100,
    2
  ) AS pct_change
FROM segment_consumption
ORDER BY
  pct_change DESC

Rhesis judge explanation

The SQL correctly handles population and filters (segment IN ('SME','LAM','KAM'), c.currency = 'EUR'), extracts years via LEFT(ym.date, 4) as the evidence indicates, and aggregates consumption per segment per year. However, the evidence explicitly defines the percentage calculation as (consumption_2013 - consumption_2012) / consumption_2013 * 100, while the SQL computes (consumption_2013 - consumption_2012) / NULLIF(ABS(consumption_2012), 0) * 100, dividing by the 2012 base instead of the 2013 consumption specified by the expert evidence.
