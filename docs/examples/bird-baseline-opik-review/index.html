BIRD Baseline: Opik Evaluation and Review

Created: 2026-10-24 · Updated: 2026-10-25

The official BIRD result remains 9 of 30 questions (30%). The updated Opik suite adds a per-question Gold SQL comparison and passes 17 of 30 cases. That Gold SQL judgment agrees with the official result on 20 of 30 questions: it marks 9 official mismatches as passes and one official match as a failure. The official score remains the benchmark result; the Opik pass rate is a separate judge opinion.

NO SQL PAIR KNOWLEDGE

SQL Pair Knowledge was NOT USED by the NL2SQL system. This review preserves the original five-table pilot, questions, evidence, generated SQL, full result rows, and scores. The Opik run generated no new SQL. The updated test suite gives its judge each question's Gold SQL as an evaluation reference; the original SQL-generation run never received it.

Read the baseline workflow for data preparation and the 30-question analysis for side-by-side reference and actual results. This guide explains how to inspect the evaluation in Opik.

Companion guide: Rhesis evidence-based semantic review​

The separate Rhesis Guide: BIRD Evidence-Based Semantic Review runs the same 30 questions with BIRD evidence available to a Rhesis judge only. It explains the three judge outcomes, the 20/30 result, and why this semantic review is not directly comparable to official BIRD Execution Accuracy.

1. Dataset v1​

In the project sidebar, choose Evaluation → Datasets, then open bird-debit-f65faf4a-no-sql-knowledge-20261024. Select v1 and open Records. Search a question_id to inspect one case. Use Columns to show evidence, gold_sql, and question_id if they are hidden. The dataset has 30 items; its locked version is 01a16cdd-e44a-7565-b9d7-faa5dbb98333.

COPY THIS DATASET TO A COMPANY OPIK WORKSPACE
  1. Download the 30-question input dataset to reproduce the original dataset version.
  2. Download the Gold SQL review CSV to reproduce this frozen Opik review, including Gold SQL, saved SQL, and both result tables.
  3. In the destination project, upload the CSV through Evaluation → Datasets → Create new dataset. Use question and evidence as the task input; keep Gold SQL and saved rows as evaluation references.

The input CSV copies dataset records only. The Gold SQL review CSV preserves the archived task inputs, generated SQL, Gold SQL, result rows, official scores, and assertion outcomes; it does not copy Opik experiments, traces, or review queues. See Opik's CSV dataset upload guide.

Show the four actions inside the Datasets view

In Datasets → Records, use Columns to expose or hide fields, search a question ID to locate one case, open Version history to confirm the pinned version, and use the dataset's Run experiment action only after a task and scoring metrics have been configured. This baseline replay links to v1 and measures stored outputs; it did not ask the app to generate new SQL.

The dataset stores evaluation references; the original generation request and trace confirm the model did not receive SQL Pair Knowledge. The score comparison below uses this same dataset version. Test Suite v2 is a separate collection with each question, evidence, and Gold SQL.

2. Experiments​

In the project sidebar, choose Evaluation → Experiments and compare the original baseline with bird-opik-review-20261024-2038-gold-sql official metrics. The comparison link opens on the Results tab; choose Feedback scores to compare the recorded metrics. Return to Results to search a question ID and open its row for the saved SQL and result rows.

Start with the original run. Its summary shows the complete-result match rate, average request time, errors, and timeouts.

The official exact-match implementation compares full rows. An extra or missing column changes the result, even if one value is correct. Duplicate rows and row order are ignored.

THE PARTIAL ANSWER SCORE DEPENDS ON ROW ORDER

The official partial answer score code removes duplicate rows, then compares rows by their returned positions. Row order can change the score. It does not prove that filters or formulas are equivalent and adds no numeric tolerance.

Case 1506 returns the same 21 descriptions and passes the exact answer match, but its partial answer score is 0.190476 because the rows are ordered differently. Case 1533 is also affected by row order. We ran the official calculation without sorting or changing it. BIRD's Mini-Dev README describes this as a beta metric. Use it as a diagnostic, not as a business acceptance score.

3. Test suite​

Open the BIRD Gold SQL test suite, version 2. It contains 30 question records with their evidence and Gold SQL. Open the suite run results to search a question ID and inspect the saved SQL and rows.

For this frozen replay, the task input is the saved question and evidence. The task output contains the saved generated SQL and result rows plus that case's Gold SQL. The judge did not call NL2SQL or execute either query. Gold SQL is an evaluation reference, not generation knowledge.

The first three checks cover population and dates, calculation and grouping, and the requested answer. The fourth asks whether the saved SQL is logically equivalent to the Gold SQL. All four are natural-language assertions judged by a model; none runs SQL. The official result comparison remains separate and checks the complete saved result rows.

Opik checked each case once and required one passing run. 17 of 30 passed all four checks; the dashboard rounds this to 57%. The Gold SQL comparison alone passed 17 cases and agreed with the official result on 20. The full list of results and reasons is available in the suite report.

The judge and official result disagree on 10 questions. It passed 9 cases whose complete output differed from Gold: 1471, 1472, 1476, 1480, 1484, 1486, 1493, 1528, and 1533. Most add columns or rows that the BIRD exact comparison counts as mismatches; case 1493 also rounds the answer. It failed case 1509, although the saved result matches Gold on this fixed database: the SQL uses a different date boundary, and the judge would not assume the two queries are equivalent without executing them. The judge has no database access, so this comparison is advisory.

Show the earlier three-check suite for comparison

The earlier suite did not include Gold SQL and recorded 26 of 30 automated passes. Its output is preserved in the original suite report. Version 2 keeps that run intact and adds the Gold SQL comparison as a fourth check.

AUTOMATED CHECKS ARE NOT EXPERT VERDICTS

The automated judge uses the same model family as the SQL generator, and its randomness setting was left at the default. It receives the question and evidence, saved SQL and rows, and that case's Gold SQL. It does not receive database structure, Gold result rows, or database access. It cannot establish execution equivalence from the Gold SQL text.

The Gold SQL comparison still overclaims correctness on nine cases and misses one official match. For example, it treats extra result columns as harmless for questions 1471 and 1484, although BIRD compares the complete result table. For question 1498, the new Gold comparison correctly fails the saved SQL; the earlier three checks passed it despite the wrong monthly calculation. It also rejects 1509 because it cannot determine whether the different date boundary changes results on the fixed database. Keep the official result score as the benchmark measure and review disagreements with a person.

Use expert-reviewed examples to check whether an automated judge agrees with people, as described in Opik's judge-alignment guide. Evaluation guidance also recommends combining fixed checks, automated review, and human review.

This evaluation checks saved outputs; it does not run NL2SQL again. The task returned the saved SQL and results with the per-question Gold SQL reference and made no generator calls. The judge comparison is advisory; the official result match remains the regression score. The UI's Run button alone does not run this project's SQL generator.

4. Annotation queue​

In the project sidebar, choose Evaluation → Annotation queues and open the Gold SQL review queue. It contains 30 saved experiment traces from this replay. No human feedback has been submitted.

Choose Annotator's view and Start annotating.

  1. Select a case, starting with 1472, then 1479.
  2. In Input, read the original question. Open the matching case in Dataset v1 or Test Suite v2 to read its Gold SQL.
  3. In Output, inspect the saved generated SQL, Gold result rows, actual rows, and official scores. The 30-question analysis shows reference and actual results side by side.
  4. Submit 👍 or 👎 and a reason only when the evidence supports a decision. Leave unclear cases unscored and add a comment for a domain expert. Use Trace to read the saved notes.

Keep three results separate: the official comparison of returned rows, the Opik judge's four pass/fail checks, and human feedback. The partial answer score measures overlapping values and can change with row order. An automated pass is not human approval, and an unanswered queue item is not a zero.

Compare baselines​

For a changed model or prompt, use the same dataset version, database, official score, and four checks. Review each question for changes. A different judge or different assertion wording can change the pass rate even when the generated SQL is unchanged.

Keep the official 9 of 30 result matches visible. Do not present the 35.95% partial answer score, the 17 of 30 suite passes, or the 20 of 30 judge agreements as improved BIRD accuracy. External scores are comparable only when the question set, reference answers, database, evidence, and scoring rules match. This 30-question pilot is not a full BIRD leaderboard result. See the baseline comparison boundaries.

Reproduce a new evaluation of these saved outputs

Run from the repository root with a new, nonexistent output directory. The command creates new local Opik objects and calls the configured judge; it replays saved SQL and results and does not regenerate NL2SQL predictions.

script/evaluation/.venv/bin/python script/evaluation/review_bird_opik.py \
  --records docs-site/static/datasets/bird-baseline-record-analysis/records.json \
  --baseline-run docs/20261024_evaluation/runs/bird-debit-baseline-full-20261024-0800 \
  --dataset-lock docs/20261024_evaluation/bird-opik-dataset.json \
  --policy docs/20261024_evaluation/opik-review/policy.json \
  --evaluator docs/20261024_evaluation/opik-review/evaluation_f1.py \
  --model-env src/backend_py/.env \
  --output-dir /path/to/new-review-run

API credentials stay in the local environment file. This run's judge was not independently calibrated, repeated for stability, or given retrieved schema. Analyst notes are explicitly attributed and do not impersonate human domain approval.
