BIRD Mini-Dev V2 SELECT core CSV and NL2SQL example

Created: 2026-09-25 15:20:39 +08:00 · Updated: 2026-10-24 16:39:49+08:00

This walkthrough traces a BIRD Mini-Dev V2 dataset from its official source to project-owned CSV tables, then shows how to inspect the model and compare an NL2SQL answer with the data. It follows the same source → tables → question/SQL → local result path as Spider 1.0 CSV and NL2SQL.

Historical demonstration and current baseline

The screenshots on this page preserve the earlier multi-domain demonstration; it is not the controlled 30-question baseline. For the current Draft → Publish workflow, measured results, Opik walkthrough, and external comparison, read BIRD baseline: from an empty POC to Opik results.

The historical demo project contains five selected domains: california_schools, debit_card_specializing, student_club, superhero, and formula_1. Together they contain 39 tables, 283 columns, and 999,373 rows. This is a hand-selected 226-question subset of the 500-question BIRD SELECT core, not a full official benchmark run.

1. Find and download the official source​

BIRD Mini-Dev V2 has two relevant sources: the BIRD Mini-Dev repository describes the release, and the BIRD Mini-Dev dataset on Hugging Face publishes the core questions and SQL. The SQLite databases are distributed separately in the official database package.

The downloaded minidev_0703.zip is about 763 MiB and contains the 11 source SQLite databases. The archive is large; only selected database tables are exported for this POC.

The separate Hugging Face dataset page contains the benchmark questions and SQL:

The dataset is licensed CC BY-SA 4.0. Keep the BIRD Team / BIRD-SQL attribution and license with redistributed derivatives.

2. Export the selected SQLite tables as CSV​

The official database package contains SQLite databases, not one CSV per table. For this POC, the selected tables were exported from those SQLite files as CSV, preserving the source rows. For example, after extracting the archive:

mkdir -p /tmp/bird-mini-dev-v2-source
unzip -q /path/to/minidev_0703.zip -d /tmp/bird-mini-dev-v2-source

sqlite3 -header -csv \
  /tmp/bird-mini-dev-v2-source/minidev/MINIDEV/dev_databases/debit_card_specializing/debit_card_specializing.sqlite \
  'SELECT * FROM transactions_1k' \
  > /tmp/transactions_1k.csv

The files prepared for this POC are in poc-csv-benchmark/bird-mini-dev-v2-select-core/databases/<database>/tables/. Each domain folder also has:

  • manifest.json: source table names, CSV names, column types, sample values, row counts, and file sizes.
  • import-types.json: a reference export of earlier type choices. The current CSV review detects types from the selected file contents; users can still edit any proposed type.
  • qa.csv and qa.jsonl: natural-language question, evidence, official SQL, and a PostgreSQL SQL variant using the normalized CSV column names.

For the current demo, the selected export is 35,079,411 bytes (about 33.45 MiB), below the 100 MiB batch limit. The whole nine-database candidate pack is larger than one batch, so it is not what was uploaded to demo.

3. Upload and review CSVs in the project Import dialog​

Open Schema / Modeling. Start at the empty model canvas, then select Import:

Choose CSV data in the Import dialog. The following configuration, review, and import actions stay inside this dialog:

Choose the CSV files from the five selected domains. The complete 39-file batch is about 33.45 MiB, below the 100 MiB batch limit. The dialog accepts multiple files and does not overwrite existing tables:

Review the suggested PostgreSQL table names, columns, detected types, sample values, and row counts. In this implementation the importer inspects the CSV rows to infer types; you can still change a proposal before import. transactions_1k.csv is 1,000 rows by nine columns:

In the current UI, select Create schema after Review and confirmation. This loads the CSV rows and creates a Draft. Then choose Deploy, review and confirm Publish, and check readiness before running QA. New QA uses the Active Snapshot; importing data alone does not activate the Draft. See the current seven-step Guide.

After Publish and readiness verification, inspect CSV data for query status. The following historical screenshot records 39 Queryable tables in the earlier demo; it does not show that a newly imported Draft is already active:

The CSV exports do not carry primary/foreign key constraints. For join-heavy questions, review model relationships before interpreting benchmark accuracy. For cleaner NL2SQL comparisons, use one BIRD database per project; mixing domains makes table selection less controlled.

4. Ask the question in NL2SQL QA Console​

Open NL2SQL QA Console. Keep execution mode on MCP and confirm the project is demo and Ready. Enter the question shown by the QA page:

How many core business records are there?

Submit the question and inspect the response. The console interpreted “core business records” as customers, gas stations, products, and transactions, generated SQL for each table, and executed it in PostgreSQL:

WITH core_entity_counts AS (
  SELECT 'customers' AS business_entity, COUNT(*)::BIGINT AS record_count FROM customers
  UNION ALL SELECT 'gas stations', COUNT(*)::BIGINT FROM gasstations
  UNION ALL SELECT 'products', COUNT(*)::BIGINT FROM products
  UNION ALL SELECT 'transactions', COUNT(*)::BIGINT FROM transactions_1k
)
SELECT business_entity,
       record_count,
       SUM(record_count) OVER () AS total_core_record_count
FROM core_entity_counts
ORDER BY record_count DESC, business_entity ASC;

This is a local demo question, not an official BIRD benchmark question. The phrase “core business records” is intentionally interpreted by the model from this project's debit-card dataset; the result includes four entity tables, rather than only counting transactions_1k. For an official BIRD comparison, debit_card_specializing question 1509 asks how many Czech gas-station transactions occurred after 2012-01-01. Its PostgreSQL Gold SQL is in the local qa.csv; it joins transactions_1k with gasstations and counts qualifying transaction IDs.

5. What this example does and does not benchmark​

The 226 questions bundled with the five imported domains are useful for checking whether NL2SQL selects the right tables and columns, forms joins, filters, and aggregates. The QA Console run above exercised multi-table selection, UNION ALL, aggregation, SQL validation, PostgreSQL execution, and result rendering. The four returned entity counts sum to 39,768.

This is not a published BIRD score or a controlled performance benchmark. For a fair benchmark, use one BIRD database per project, execute the official questions for that database, and compare result rows with the matching Gold SQL result. Fix the PostgreSQL version, imported types, model relationships, indexes, cache state, timeout, and repetitions before comparing latency. CSV ingestion also omits keys and indexes unless they are added separately, so local timing is not directly comparable to the benchmark's source database.
