Health and Readiness APIs

Created: 2026-09-21 12:48:12 +08:00 · Updated: 2026-10-12 23:54:03 +08:00

GET /api/health is cheap liveness; it performs no dependency or QA calls.

For copy-ready checks with response samples and field explanations, see Check project health and troubleshoot.

POST requestChecksResponse
/api/health?mode=systemShared control-plane DB, one chat probe, embedding, pgvector.system, .errors
/api/health?mode=project&projectId=equityCurrent Active bundleHash, derived material, query-side DB.project.qaAvailable, .project.runtime, .project.errors
/api/health?mode=smoke&projectId=equityOne real MCP Ask.smoke.status, .smoke.bundleHash, .smoke.ask
/api/health?mode=fullSystem once, then all projects serially.system, .projects[projectId].qaSmoke, .errors

project and smoke require a registered projectId; system and full reject it. Invalid parameters return HTTP 400 before probing. Completed diagnostics return HTTP 200 with structured errors. Smoke is one attempt (passed, failed, or not_run), and a failed Ask does not change the current Active or project qaAvailable.

Run checks with curl, without the UI​

These commands call the local FastAPI backend directly on its default development port (4000). They need no request body. If your backend uses another port, use that port in the URL. The e2e mock backend defaults to 12345.

Check that the backend is responding:

curl -sS 'http://127.0.0.1:4000/api/health' | jq .

Check shared services, including the chat LLM, embedding provider, and vector-query capability. This makes one chat probe and one embedding probe:

curl -sS -X POST 'http://127.0.0.1:4000/api/health?mode=system' | jq '{mode,status,failedChecks:[.system.checks[] | select(.status != "ready") | {key,label,status,summary,details,reasonCode,nextAction,diagnostics}],errors}'

Check one project's Active Snapshot, Schema RAG, and business database. This does not run an Ask:

project_id='fund'; curl -sS -X POST "http://127.0.0.1:4000/api/health?mode=project&projectId=${project_id}" | jq '{mode,status,qaAvailable:.project.qaAvailable,bundleHash:.project.bundleHash,failedChecks:[(.project.runtime.checks // [])[] | select(.status != "ready") | {key,label,status,summary,details,reasonCode,nextAction,diagnostics}],errors:.project.errors}'

Run one real MCP Ask for the project. This is the no-UI equivalent of QA Smoke and may call the configured LLM. The health endpoint resolves the project's configured Ask tool and uses the MCP client internally; you do not need to handcraft MCP headers or a session:

project_id='fund'; curl -sS -X POST "http://127.0.0.1:4000/api/health?mode=smoke&projectId=${project_id}" | jq '{mode,status,smokeStatus:.smoke.status,summary:.smoke.summary,details:.smoke.details,bundleHash:.smoke.bundleHash,ask:.smoke.ask,errors}'

Call an MCP tool directly with curl​

Use this when you want to test a custom question rather than the fixed QA Smoke question. First discover the tool name from the selected project's tools/list response. In the live equity project, that response lists equity_ask and equity_saerch_test:

curl -sS -N --max-time 30 'http://127.0.0.1:4000/mcp/equity/' \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -H 'MCP-Protocol-Version: 2026-07-28' \
  -H 'Mcp-Method: tools/list' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{"name":"curl","version":"1.0"},"io.modelcontextprotocol/clientCapabilities":{}}}}'

The response is a JSON-RPC result with resultType: "complete"; the live equity tool names include equity_ask and equity_saerch_test. The full list entries also include each tool's description and inputSchema.

For another project, replace equity in the path and use a name from that project's response. Then edit the variables below. The same tool_name is sent in both Mcp-Name and JSON-RPC params.name:

api_base='http://127.0.0.1:4000'
project_id='equity'
tool_name='equity_saerch_test'
staff_id='guest'
qa='How many core business records are there?'
curl -N -sS "${api_base}/mcp/${project_id}/" \
  -H 'Accept: application/json, text/event-stream' \
  -H 'Content-Type: application/json' \
  -H 'MCP-Protocol-Version: 2026-07-28' \
  -H 'Mcp-Method: tools/call' \
  -H "Mcp-Name: ${tool_name}" \
  -H "X_ABC_STAFF_HEADER: ${staff_id}" \
  -d "$(jq -n --arg tool_name "$tool_name" --arg qa "$qa" '{jsonrpc:"2.0",id:2,method:"tools/call",params:{name:$tool_name,arguments:{query:$qa},_meta:{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientInfo":{name:"curl",version:"1.0"},"io.modelcontextprotocol/clientCapabilities":{}}}})"

The live equity call produced an SSE event: message whose data: contains this abbreviated JSON-RPC response (generated IDs and long reasoning text omitted):

{
  "jsonrpc": "2.0",
  "id": 4,
  "result": {
    "resultType": "complete",
    "content": [{
      "type": "text",
      "text": "{\n  \"status\": \"success\",\n  \"confidence\": 0.9,\n  \"query\": \"How many core business records are there?\",\n  \"results\": [{\"core_business_record_count\": 1446}],\n  ..."
    }],
    "isError": false,
    "structuredContent": {
      "status": "success",
      "bundleHash": "<Active Snapshot hash>",
      "confidence": 0.9,
      "query": "How many core business records are there?",
      "results": [{"core_business_record_count": 1446}],
      "sql": "SELECT COUNT(DISTINCT fund_code) AS core_business_record_count FROM fund_master_view;",
      "meta": {"mode": "SQL_EXECUTE_RESULT", "timing": {"totalDurationMs": 19939}},
      "reason": {"answer": "<answer explanation>", "business": "<business reasoning>", "technical": "<technical analysis>"},
      "queryId": "<generated query ID>",
      "threadId": "<generated thread ID>",
      "traceId": "<generated trace ID>",
      "suggestedQuestion": ["<follow-up question>"],
      "groundReason": "<grounding explanation>"
    },
    "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "NL2SQL MCP Server - equity", "version": "1.0.0"}}
  }
}

content[0].text contains the historical business JSON as text, while structuredContent exposes the same result as an object for clients that support it. resultType and isError are MCP call status; structuredContent.status is the NL2SQL business outcome. The live count, hash, IDs and reasoning vary by request and Active Snapshot.

This is the project's current stateless MCP request shape. It does not need an initialize request or Mcp-Session-Id. The selected project and tool name must exist in the active MCP configuration.

For all registered projects, run the shared checks once and then project checks and Smoke serially:

curl -sS -X POST 'http://127.0.0.1:4000/api/health?mode=full' | jq '{mode,status,systemStatus:.system.status,projects:[.projects[] | {projectId,status,qaAvailable,smokeStatus:.qaSmoke.status,smokeDetails:.qaSmoke.details}],errors}'

full waits for the complete report and can run one Ask for each project whose runtime is ready. Use it for manual troubleshooting, not as a startup, liveness, or Kubernetes probe. The default identity is guest; to send a staff identity, use the configured HTTP_STAFF_HEADER header. For the default local header, that is X_ABC_STAFF_HEADER.

Read the returned JSON status, not just curl's exit code: a completed diagnostic can return HTTP 200 with a non-ready status such as failed, partial, or setup. For an LLM/Ask failure, inspect .smoke.details and .smoke.ask.details; for runtime failures, inspect the failed check's details, reasonCode, and nextAction. Keep -f off curl so it does not hide a structured error response.

Unpublished changes are inspected separately with GET /api/artifact-versions/freshness?projectId=equity.
