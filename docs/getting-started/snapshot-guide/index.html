Export, edit and import a Snapshot

Created: 2026-10-11 · Updated: 2026-10-11

Open Guide → Snapshot. Select any step to find its existing control; you can start at Export when an Active Snapshot already exists.

Snapshot is the authority for NL2SQL configuration. It carries models, knowledge, runtime policies, MCP tools, and Prompt files. The database stores the environment's runtime data.

1. Publish​

In UAT, review the Draft and click Publish. It becomes Active and its ZIP downloads automatically. New QA uses this Active Snapshot.

To rebuild runtime without changing business content, choose Current Active Snapshot in the same Publish dialog. This preserves a different Unpublished Draft. Runtime warnings do not disable recovery; an actual build failure is reported and does not replace the committed source.

2. Export​

Click Export to download the current Active package. You do not need to Publish again. Unpack the ZIP to inspect or edit the files.

3. Understand the Snapshot files​

Select a file in Configuration → Active Snapshot → Unpublished changes. Click Field mapping beside its filename. The application opens the file’s existing UI and shows the shared Guide popup there.

Model columns​

Choose semantic/modeling-state.json, then Field mapping. In Schema, choose the model and column. The Guide shows that record’s Draft JSON and points to the corresponding real Columns field. Click a key or use Previous / Next to switch fields.

Snapshot keySchema field
models[].columns[].nameName
models[].columns[].aliasAlias
models[].columns[].dataTypeType
models[].columns[].descriptionDescription
models[].columns[].isPrimaryKeyPK tag; false means no tag

Question-SQL pairs​

Choose knowledge/sql-pairs.json, then Field mapping. In Knowledge, select the record. Its ID locates the actual row, including when the record was not on the initial table page.

Snapshot keyKnowledge field
[].questionMatching question
[].sqlSQL statement
[].is_enabledEnabled
[].provenanceSource; manual displays Manual

Instructions​

knowledge/instructions.json is marked Beta function · ignored. Field mapping for Instructions is not included in this Guide; its existing feature and Snapshot import/export remain available.

Prompts, policies and tools​

A file in prompts/ opens the corresponding System or User prompt in Prompt workspace. Prompt files are TXT, not JSON. Snapshot View shows all prompt content; Export includes the actual saved TXT files and their exact whitespace; absent files are not synthesized from templates. The example below uses a prompt edited and saved through the real UI before Publish.

config/portable-environment-agnostic-config.json opens Diagnostics → Effective configuration → Active runtime policies. Select a key to locate its real policy field.

config/mcp-tools.json opens NL2SQL QA → API Info. Choose a tool to compare its description with the actual tool description. Its annotations control visible tool hints; inputSchema defines the arguments shown by View Schema.

knowledge/logical-views.json opens Semantic Views in Schema. Select a record to locate its Name, Description and read-only SQL statement. Empty files show No records in this file, without inventing an example record.

manifest.json describes the package format and file paths. semantic/business-metadata.json holds business labels, descriptions, tags and value options. Their existing viewing surface is the Snapshot viewer; they have no separate business-field editor.

The popup labels its JSON Unpublished Draft. Active content and Active-only UI surfaces can differ. Business names and values identify configuration; system IDs are not exported. Created time is audit information and is not an exported field. Guide navigation does not edit, save or publish content. Return to Snapshot preserves the selected file; close the popup or press Escape to continue normal work.

Check the actual hash input​

In View → Hash content, select a file to inspect the exact business fields used by diff and SHA-256. Copy the complete canonical input to independently recompute the fingerprint. Excluded fields show their file path and reason. A stored hash mismatch is displayed without rewriting the binding.

Expected system IDs, audit fields and standard package metadata are informational exclusions; normal Export and Import do not show warnings. In Import, click package metadata fields excluded from business content to expand the exact excluded paths and reasons; this section starts collapsed and also supports Enter. Business Schema fields determine what is imported; arbitrary undeclared fields/files are ignored with a warning summary and expandable details. Import logs WARN with every ignored path and reason. Indexed records (items/order) are read as business records, retaining valid business order; system identity is not an import prerequisite. Unparseable business content, ambiguous references and unsafe archives stop import before any data is replaced. Runtime readiness is checked separately; provider failures do not disable configuration transfer.

4. Package for import​

Edit the corresponding files using your own editor. Preserve business names, unrelated values, and business order. System IDs and audit metadata are informational exclusions. ZIP the complete Snapshot folder, including manifest.json, config/, knowledge/, semantic/, and prompts/. Include unchanged files and all files in the original export, including those not described by the Normal view.

5. Import​

Open the target environment's project. Choose Active Snapshot → Import and upload the ZIP or full folder. Validation runs automatically; click Import after it reports OK. Valid business content becomes the selected Active Snapshot before runtime synchronization. If synchronization fails, the response explains why; that same Active content remains available in View and Export. Health and QA report the failure until its matching runtime is rebuilt.

6. Check readiness​

In Diagnostics, click Refresh report. Confirm readiness is ready and QA available is shown.

7. Try Ask​

In NL2SQL QA, send a representative question and check its SQL, answer, and result.

Existing deployment options​

The same package can be imported through POST /api/artifact-versions/import-upload, or from a server-accessible folder through POST /api/artifact-versions/import. Startup import uses PROJECT_<ID>_ARTIFACT_ACTIVE_SNAPSHOT_IMPORT_DIR. These are existing deployment options.

Snapshot export/import does not move runtime table rows or perform DDL/data migrations. The target environment must provide the required datasource, business objects, and access for readiness and QA to pass.

The actual application Guide defines this journey. e2e/mock-poc-csv-reset.spec.ts, run by script/e2e-mock/11_run_poc_csv_reset.sh in the 99 suite, verifies the same controls, edited ZIP import, Active content, readiness, and expected QA result. After the whole journey passes, the same screenshot buffers are attached to Monocart and copied to this docs-site.
