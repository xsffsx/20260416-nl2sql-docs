Understand the Thought Chain

Created: 2026-10-17 · Updated: 2026-10-17

The Thought Chain explains how your question becomes an answer: understanding, knowledge and instruction retrieval, schema selection, planning, SQL generation, validation, any corrections, execution, and answer rendering.

Open NL2SQL QA → Copilot Ask, choose your project, then open Guide → Thought Chain. All steps always shows the complete navigation in one vertical list. There is no expand or collapse control. Use it to jump to a stage, or use Next to follow them in order. The highlighted area is the actual control or evidence for the selected question. Opening the Guide does not run another question or correction.

Every executed step can contain:

  • Input Context: what that step received.
  • Thinking: model-provided reasoning, when available. An absent lane means none was supplied.
  • Output: what that step produced, including its actual error if it failed.
  • JSON controls: structured details for the corresponding input or output. Expand them or use Copy JSON when you need the complete evidence.

Completed describes that stage only. A generated SQL candidate can still fail validation. Earlier failures stay visible even when the final answer succeeds. Not executed for this ask means the stage did not run, rather than implying success.

The following screenshots use the passing scenario 03 mock E2E, with controlled model responses and a real PostgreSQL query database. Its missing-column error is deliberately arranged in test fixtures; ordinary questions do not have to fail. The correction example requires executable database mode. The SQL-only import tutorial demonstrates generation without executing business rows.

Ask a question​

Enter a question and submit it with the arrow button. The selected project's Active Snapshot supplies the business context. In the isolated mock example, enter:

Count funds and verify SQL correction recovery.

Expected: the question appears in the conversation and its actual execution steps become available.

Understanding​

Select Understanding under All steps. Explain what you are asking before searching for data.

  • Input Context: Your question and conversation context.
  • Output: The interpreted question and selected intent.

Expected: the highlighted step shows this question's actual evidence and stage status.

SQL Pair RAG​

Select SQL Pair RAG under All steps. Find relevant question–SQL examples in project knowledge.

  • Input Context: The question used to search knowledge.
  • Output: Retrieved examples and their relevance. No matches is a valid result.

Expected: the highlighted step shows this question's actual evidence and stage status.

User Instructions​

Select User Instructions under All steps. Find the project instructions that apply to this question.

  • Input Context: The question and instruction context.
  • Output: Selected business rules that guide the answer.

Expected: the highlighted step shows this question's actual evidence and stage status.

Schema Linking​

Select Schema Linking under All steps. Identify the tables and columns needed for the question.

  • Input Context: The question and available schema context.
  • Output: The selected schema and relationships used to write SQL.

Expected: the highlighted step shows this question's actual evidence and stage status.

Reasoning​

Select Reasoning under All steps. In normal mode, plan how to answer the question.

  • Input Context: The question, schema, examples, and applicable instructions.
  • Output: The query plan used by Generating.

Expected: the highlighted step shows this question's actual evidence and stage status.

Generating​

Select Generating under All steps. In normal mode, turn the plan into a SQL candidate.

  • Input Context: The query plan and its supporting context.
  • Output: The complete generated SQL. It still needs validation.

Expected: the highlighted step shows this question's actual evidence and stage status.

Reason and Generate​

Select Reason and Generate under All steps. In Fast mode, planning and generation run together. This replaces the separate Reasoning and Generating stages.

  • Input Context: The question, schema, examples, and applicable instructions.
  • Output: The query plan and complete SQL candidate. The mock example initially produces SELECT missing_column FROM fund_master_view.

Expected: the highlighted step shows this question's actual evidence and stage status.

Validating​

Select Validating under All steps. Check whether the SQL is valid before running it. Select Check 1 · Failed to inspect the initial failure.

  • Input Context: The exact SQL, attempt number, and validation mode. In this example, attempt is 0 and mode is explain.
  • Output: The verdict and original error. PostgreSQL reports column "missing_column" does not exist; Output JSON retains isValid: false and outcome: "error".

Expected: the highlighted step shows this question's actual evidence and stage status.

Correcting​

Select Correcting under All steps. Use the validation error to produce a new candidate. Read the previous SQL alongside the error before inspecting the new SQL.

  • Input Context: The previous SQL, original error, and retry budget.
  • Output: The corrected candidate or actual correction failure. Here the model returns SELECT COUNT(*) AS total_funds FROM fund_master_view. A completed correction does not mean the candidate has passed validation.

Expected: the highlighted step shows this question's actual evidence and stage status.

Return to Validating and choose Check 2 · Passed. Confirm that the corrected COUNT statement passed its own database validation at attempt 1. Each additional check retains its own SQL and verdict; the first failure remains failed.

When no correction is needed, Correcting says Not executed for this ask. If the allowed corrections are exhausted, select Retry limit · Failed in Correcting. The ask ends with Exceeded correction retries, retains the preceding diagnostics, and does not claim a successful answer. A zero budget allows no correction model calls.

SQL Execution​

Select SQL Execution. This stage runs the validated SQL against the project's query database.

  • Input Context: the SQL actually sent for execution.
  • Output: the returned rows and columns, or the original execution error.

Expected: the controlled example returns one row containing total_funds: 1446. Your project's data determines its own result.

Answer Rendering​

Select Answer Rendering. This stage turns the verified result into the answer shown in the conversation.

  • Input Context: the question, executed SQL, and returned data.
  • Output: the user-facing answer and supporting result.

Expected: the final answer agrees with the executed result. Generation alone does not prove the answer was executed successfully.

Reopen history​

Close the Guide and reopen the question from conversation history. Refresh the page, then select Guide → Thought Chain → All steps → Reopen history.

Expected: the question retains the same steps, failed SQL, correction candidates, original errors, and final result. Editing Draft later does not rewrite this completed run. Visiting the Guide does not mark this verification complete.

Verify this walkthrough​

Run bash script/e2e-mock/03_run_non_json_error.sh for the focused scenario or bash script/e2e-mock/99_run_all_e2e-and-report.sh for the full mock suite. The scenario verifies API-to-DOM evidence, JSON copy, real correction, exhaustion, zero budget, normal/Fast success, refresh/history, and Snapshot preservation.

Each image uses the identical PNG attached to its Monocart report. The complete image set is published only after the scenario passes; a failed run preserves approved images.
